1. เหตุผลที่โปรเจกต์นี้เลือก SQLite แทน MongoDB

ข้อมูลของระบบมีโครงสร้างคงที่และมีความสัมพันธ์ระหว่างตารางชัดเจน ตาราง requests เก็บข้อมูลคำร้อง และทุกคำร้องต้องระบุผู้ยื่นได้ ระบบจึงกำหนด Foreign Key (requester_id) อ้างอิงไปยังตาราง users ฐานข้อมูลเชิงสัมพันธ์ (SQL) รองรับข้อกำหนดนี้โดยตรงผ่าน Constraints และ Transactions ซึ่งป้องกันข้อมูลผิดพลาด เช่น คำร้องที่ไม่มีเจ้าของจะบันทึกเข้าระบบไม่ได้ MongoDB เหมาะกับเอกสารที่รูปแบบเปลี่ยนบ่อยและไม่มีโครงสร้างแน่นอน ซึ่งไม่ตรงกับลักษณะข้อมูลของโปรเจกต์นี้

SQLite ยังมีข้อดีด้านการใช้งาน เพราะเก็บข้อมูลทั้งหมดในไฟล์เดียวคือ campus.db ผู้พัฒนาไม่ต้องติดตั้งหรือดูแลเซิร์ฟเวอร์ฐานข้อมูลแยกต่างหาก ทำให้การพัฒนาและการ Deploy ทำได้ง่ายขึ้น

2. ผลกระทบหากเปลี่ยนไปใช้ MongoDB

การเปลี่ยนไปใช้ MongoDB กระทบสองชั้น ได้แก่ ชั้น Service และชั้น Controller

ในสถาปัตยกรรมปัจจุบัน การเปลี่ยนแหล่งเก็บข้อมูลแก้ไขเฉพาะชั้น Service ได้ เพราะ SQLite ทำงานแบบ Synchronous ฟังก์ชันแต่ละตัวรับค่าและคืนค่าโดยตรง ชั้นอื่นจึงไม่ต้องรับรู้การเปลี่ยนแปลงด้านล่าง

Driver ของ MongoDB ติดต่อฐานข้อมูลผ่านเครือข่ายและทำงานแบบ Asynchronous ทั้งหมด ทุกเมธอดในชั้น Service จึงต้องเปลี่ยนเป็น async และคืนค่าเป็น Promise ชั้น Controller ที่เรียกใช้ Service ต้องเพิ่ม await ในทุกจุดที่เรียก หากไม่เพิ่ม โปรแกรมจะได้รับ Promise แทนข้อมูลจริง

ชั้น Route และ Frontend ไม่ต้องแก้ไข เพราะ API ยังส่งข้อมูล JSON รูปแบบเดิม ผู้ใช้งานจึงไม่เห็นความเปลี่ยนแปลงของฐานข้อมูลที่อยู่เบื้องหลัง

3. กรณีที่ต้องใช้และไม่ต้องใช้ async

ไม่จำเป็นต้องใช้ เมื่อข้อมูลอยู่ในเครื่องเดียวกับโปรแกรม เช่น การใช้ node:sqlite อ่านและเขียนไฟล์ในเครื่องโดยตรง การทำงานลักษณะนี้เสร็จภายในระดับไมโครวินาที การเขียนแบบ Synchronous จึงไม่ทำให้ประสิทธิภาพลดลง และช่วยให้โค้ดอ่านง่ายตามลำดับการทำงาน

จำเป็นต้องใช้ เมื่อต้องติดต่อฐานข้อมูลผ่านเครือข่าย เช่น MongoDB, PostgreSQL หรือฐานข้อมูลบน Cloud เวลาตอบสนองของเครือข่ายคาดการณ์ไม่ได้ หากเขียนแบบ Synchronous Node.js จะหยุดรอจนได้รับข้อมูล และคำขอของผู้ใช้รายอื่นจะถูกบล็อกไปด้วย การใช้ async/await ทำให้เซิร์ฟเวอร์ประมวลผลคำขอของผู้ใช้รายอื่นต่อได้ระหว่างรอ แล้วกลับมาทำงานที่ค้างไว้เมื่อได้รับข้อมูล
